# Mediline: оплата на сайті та автоматичне збирання USDT

## Стан реалізації

Реалізація підготовлена локально. Реальні гаманці не створювалися, приватні ключі не отримувалися,
сервіси у production не запускалися. Для активації потрібні гаманці, конфігурація інфраструктури,
контрольна оплата у Shasta та перевірка відновлення гаманця. Автоматичні тести з підставними
відповідями не замінюють переказ у справжній мережі.

- BTC: окрема адреса, QR BIP21 із сумою, спостереження через Esplora, щонайменше 3 підтвердження.
  Автоматичне збирання BTC не реалізоване; BTC можна витрачати/консолідувати окремим гаманцем.
- USDT TRC-20: окремі адреси, QR з адресою, сума окремо, перевірка точного контракту й solidified receipt.
- Покупець залишається на своєму storefront. Є EN/FR/DE/ES/IT, копіювання, таймер,
  відновлення після reload у тій самій вкладці. У пошту криптоінструкції не надсилаються,
  коли новий режим увімкнено. Звичайні листи про замовлення WooCommerce не вимикаються.
- Оплата та збирання коштів мають окремі статуси. Оплата mainnet переводить замовлення в processing,
  а не completed. Testnet не позначає реальне замовлення оплаченим.
- Pipedrive отримує оновлену примітку. Won і PAP не запускаються автоматично від криптоплатежу.

## Компоненти й межі доступу

1. Catalog Core у центральному WordPress створює замовлення та підписує запити до watcher.
2. Store Core пересилає статус лише для свого магазину й за ключем конкретного замовлення.
3. `server.mjs` (watcher) має тільки публічні branch keys, реєстр рахунків і доступ на читання мереж.
4. `signer/worker.mjs` працює окремим процесом/контейнером без вхідного HTTP-порту.
   Має приватний ключ **лише гілки адрес для отримання оплат**, окремий ключ gas-гаманця
   і публічну адресу treasury. Ключ treasury йому не потрібний.

WordPress не має доступу до каталогу секретів signer. Не розміщувати сервіс/секрети у web root.
Node-процеси не забезпечують апаратну ізоляцію ключів: компрометація signer дає доступ до його
гарячих ключів. Для більших оборотів потрібен HSM/віддалений підписувач із власними правилами;
цей варіант поки не реалізований. У gas-гаманці тримати лише робочий резерв.

## Що налаштувати

- Окремий treasury-гаманець для надходжень USDT (його публічна адреса починається з T).
- Окремий gas-гаманець із TRX. Не використовувати treasury як gas-гаманець.
- Окремий HD-гаманець адрес замовлень і його резервну копію **поза сервером**.
  Гілка TRON: `m/44'/195'/account'/0`. Signer отримує лише приватний extended key цієї гілки,
  watcher — її xpub. Перевірити адреси індексів 0, 1, 2 у відновленому гаманці.
  Звичайна адреса біржі не дає можливості генерувати й підписувати дочірні адреси.
- Для BTC: BIP84 `m/84'/0'/account'/0` mainnet, `m/84'/1'/account'/0` testnet.
  Watcher приймає нормалізований xpub/tpub. Публічний account zpub/vpub/xpub/tpub можна
  перетворити утилітою `tools/prepare-public-wallet.mjs` (вона відхиляє приватні ключі).
- Обліковий запис/ключ API TronGrid з достатньою квотою. Власний Esplora або довірений провайдер BTC.
- Публічний HTTPS-хост watcher, наприклад окремий піддомен. TLS має завершуватися на вашому
  reverse proxy; порт 8787 відкритий лише на loopback. Не зупиняти наявний Dokploy/Traefik.
- Два різні випадкові секрети автентифікації: WordPress↔watcher і signer↔watcher.

Не надсилати приватні ключі/seed у чат, не вписувати у WordPress, шаблони або команди shell.
Установити приватні файли безпосередньо на signer: `/etc/mediline-payments/branch.key` та `gas.key`,
права 0400/0600, власник UID процесу (у прикладі 1000). Seed і ключ treasury там не потрібні.
Не копіювати справжні ключі в example-файли репозиторію. Спершу використовувати окремі тестові ключі.

## Алгоритм збирання USDT

1. Watcher бачить підтверджену оплату вчасно й пропонує рахунок signer.
2. Signer сам перевіряє derivation, точний контракт, історію підтверджених надходжень,
   суму та поточний баланс. Даних від WordPress для підписання недостатньо.
3. Якщо TRON-акаунт ще не активований, виконується окрема мінімальна активація переказом TRX.
   Її комісія враховується; отримання токенів не обов'язково активує native-акаунт.
4. Після solidification оцінюються Energy, наявні ресурси та актуальні параметри мережі.
   Резерв Energy — 20%; Bandwidth резервується окремо. **Фіксованої гарантії 7 TRX немає.**
5. Якщо TRX бракує, gas-гаманець поповнює адресу лише на дефіцит. Signer чекає підтвердження.
6. Оцінка повторюється. Якщо потрібне ще одне поповнення або перевищено ліміт — `review`,
   а не нескінченні автоматичні доплати.
7. USDT відправляється тільки на treasury з конфігурації. У БД спочатку зберігається точна
   підписана транзакція та резерв бюджету, і лише потім виконується broadcast.
8. Втрата відповіді → перевірка того самого txID, за потреби повторний broadcast тих самих байтів.
   Після expiration/помилки нова транзакція автоматично не створюється.

Одна операція збирання на рахунок. Пізні додаткові платежі, недоплати, несподівані зміни мережі
та помилки підлягають ручній перевірці. Невикористаний залишок TRX залишається на адресі;
його автоматичне повернення не реалізоване, щоб не додавати дрібних комісій.
Повернення покупцю також не автоматизоване.

Бюджети — консервативні резерви: поповнення й максимально дозволене спалювання TRX рахуються
окремо, тому резерв може бути більшим за фактичні витрати. Добовий ліміт — ковзні 24 години.
Для gas-гаманця не повинно бути інших автоматичних витрат, які ця БД не бачить.

## Запуск спочатку в тестовому середовищі

1. Скопіювати лише цей сервіс за межі WordPress. Заповнити копії example JSON у
   `/etc/mediline-payments/`, а не у web root. Створити writable UID1000 каталоги
   `/var/lib/mediline-payments/watcher` та `/var/lib/mediline-payments/signer` з правами 0700.
2. Shasta не має справжнього mainnet USDT. Потрібен тестовий TRC-20 із 6 decimals;
   його адресу задати однаково watcher і signer. Mainnet контракт відхиляється у testnet.
3. Запустити watcher через `docker compose -f compose.example.yml up -d --build watcher`.
   Налаштувати HTTPS proxy та обмежити доступ інфраструктурою, де можливо.
4. У **тестовому** центральному WordPress додати константи нижче. Namespace має бути унікальним
   для цього сайту/БД; не використовувати production namespace у клоні тестового сайту.
5. Оновити Catalog Core, Store Core й шаблони з підготовлених пакетів. Запустити
   `wp mediline-store heartbeat`, щоб checkout-тексти перейшли на оплату на сайті.
6. Перевірити повну оплату, недоплату, прострочення, не той токен, зникнення провайдера,
   повторний webhook, рестарт між підписанням і broadcast. Окремо перевірити wallet recovery.
7. Спочатку `mode: dry-run` signer. Після перевірки — `execute` **тільки testnet**,
   `docker compose -f compose.example.yml --profile signer up -d --build signer`.
   Процес запускається через `flock`: дві копії не повинні витрачати один gas-гаманець паралельно.
8. Після успішної перевірки мережі/ключів/резервних копій підготувати **окремі** mainnet-конфігурації
   та БД, указати mainnet USDT, встановити `liveApproved: true`. Провести малу контрольну оплату.

```php
define('MEDILINE_CRYPTO_ENABLED', true);
define('MEDILINE_CRYPTO_MODE', 'testnet');
define('MEDILINE_CRYPTO_URL', 'https://YOUR-WATCHER-HOST');
define('MEDILINE_CRYPTO_NAMESPACE', 'UNIQUE_SITE_NAMESPACE');
define('MEDILINE_CRYPTO_SECRET', 'WORDPRESS_WATCHER_SECRET');
```

Для mainnet USDT підтримується тільки `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t` і
`https://api.trongrid.io`. Конфігурація не дозволяє непомітно поміняти мережу, xpub,
treasury або gas-гаманець у вже наявній БД. Зміни потребують окремої міграції.

## Адмінка та експлуатація

WooCommerce → **Crypto payments**: режим, доступність watcher, список останніх рахунків,
отримана сума, статус оплати, статус збирання. У замовленні — примітки та метадані funding/sweep txID.
Pipedrive зберігає інформацію про оплату в примітці угоди; PAP працює за попередньою умовою Won.

- **Пауза збирання:** створити файл `/var/lib/mediline-payments/signer/PAUSE`.
  Нові операції перестануть запускатися; вже broadcast-транзакцію скасувати цим неможливо.
- **Зупинка:** `docker compose -f compose.example.yml stop signer`. Підтвердження оплат watcher продовжить.
- **Вимкнення WordPress-інтеграції:** `MEDILINE_CRYPTO_ENABLED=false`. Це повертає попередній
  checkout-режим і припиняє приймання криптостатусів у WordPress. Watcher/signer не зупиняються
  цією константою — керувати ними окремо. Не застосовувати як спосіб скасувати оплачені рахунки;
  для звичайної паузи збирання використовуйте PAUSE, щоб облік оплат продовжував працювати.
- **Review:** перевірити `operations` і txID на solidified node, баланс та причину в `jobs.error`.
  Не видаляти операцію і не надсилати TRX повторно навмання. Автоматичної кнопки
  «підписати ще раз» немає; повторний запуск фінансової операції потребує звірки попередньої.
- Резервувати обидві SQLite БД через штатну SQLite backup-функцію/`.backup`, а не копіювати
  лише основний файл під час роботи WAL. Реєстр адрес та журнал підписаних транзакцій критичні.
  Для відновлення з давньої копії спершу звірити видані адреси й мережеві операції офлайн;
  без цього існує ризик повторного використання індексів/неповного обліку.
- Стежити за `last_sweep`, відкладеними callback, залишком gas-гаманця, доступністю провайдера
  та журналом review. Немає сторонньої системи оповіщень: її підключення — окремий етап.
- Для малих обсягів сканування історії адрес прийнятне. Для великого каталогу оплат потрібні
  індексатор/курсор блоків і додаткові навантажувальні тести. API-провайдеру довіряємо щодо даних
  блокчейну; локальної криптографічної перевірки всього consensus/SPV тут немає.

## Перевірки

```text
npm ci --ignore-scripts
cd signer && npm ci --ignore-scripts && cd ..
npm test
php test/bridge.php testnet
php test/bridge.php mainnet
```

Тести не виконують живих переказів. Окремо проведено локальну browser-перевірку інтерфейсу
EN/FR/DE/ES/IT при ширині 1440/390, відновлення після reload, залишкової суми недоплати
і приховування QR після оплати. Production E2E/реальний Shasta переказ ще не проведені.
Compose-конфігурація перевірена парсером. Збирання Docker-образів локально не виконане:
Docker Desktop daemon у поточному середовищі не запущений.

Офіційні протоколи: [TRON confirmation](https://developers.tron.network/docs/confirmation-semantics),
[energy estimation](https://developers.tron.network/reference/estimateenergy-2),
[sign/broadcast](https://developers.tron.network/docs/api-signature-and-broadcast-flow),
[Esplora](https://github.com/Blockstream/esplora/blob/master/API.md),
[BIP32](https://github.com/bitcoin/bips/blob/master/bip-0032.mediawiki).
